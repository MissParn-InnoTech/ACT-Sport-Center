# การวิเคราะห์ข้อมูลเดิม และการปรับ Database Schema (v2)
## ระบบจัดการครุภัณฑ์และอุปกรณ์ศูนย์กีฬา — Assumption College Thonburi

เอกสารนี้อ่านคู่กับ `sports-center-asset-system-design.md` (v1) โดยปรับตามข้อมูลจริงในไฟล์ทะเบียนครุภัณฑ์ปีการศึกษา 2568

---

## 1. สรุปสิ่งที่พบในไฟล์เดิม

ไฟล์เป็น **ใบตรวจนับครุภัณฑ์ประจำปี** (มีช่องลงนาม 3 ระดับ: ผู้รับผิดชอบ → หัวหน้าหน่วยงาน → ผู้ตรวจสอบ) ไม่ใช่ระบบทะเบียนที่ใช้งานประจำวัน — จุดนี้สำคัญ เพราะระบบใหม่ต้อง **พิมพ์เอกสารชุดนี้ออกมาได้เหมือนเดิม** ไม่งั้นเจ้าหน้าที่จะต้องทำงานสองที่

| # | ชีต (หน่วยงาน) | แถว | ผู้รับผิดชอบ | หมวดที่แมป | ข้อสังเกต |
|---|---|---:|---|---|---|
| 1 | สำนักงานศูนย์กีฬา | 30 | มิสกฤติยา ต่อสกุล | OFF | มีเลขครุภัณฑ์เพียงรายการเดียว (`ACT SPORT-03 4787`) |
| 2 | เทเบิลเทนนิส | 15 | ม.อนุวัฒน์ เทพประเทียน | TTN | ระบุที่เก็บชัด "ชั้น 3 ห้องเก็บของ ใต้ที่นั่ง" |
| 3 | ห้องเต้น / การแสดง | 19 | มิสกฤติยา ต่อสกุล | DAN | ปนชุดการแสดง (ชุดพม่า, ปีก, เสื้อเลื่อม) ที่ไม่ใช่อุปกรณ์กีฬา |
| 4 | เทควันโด | 21 | มิสวรรณา จิรพลานุรักษ์ | TKD | ข้อมูลคุณภาพดีที่สุด — มีราคา สถานะ และคอลัมน์ "เช็คแล้ว" |
| 5 | กอล์ฟ | 15 | (ว่าง) | GLF | จำนวนบางช่องเป็นข้อความ เช่น "6 แผ่น", "2,000" |
| 6 | ปีนหน้าผา | 40 | ม.ชาญวิทย์ พึ่งอิ่ม | CLB | ปนครุภัณฑ์สำนักงานที่ "ย้ายออฟฟิต" แล้ว |
| 7 | สนามกีฬากลาง (รวม) | 111 | ม.ชาญวิทย์ พึ่งอิ่ม | TEN+FBL+FUT+BKB | **ชีตปัญหาที่สุด** — 4 กีฬาปนกัน + ไม้เทนนิสแยกรายอัน 30 บรรทัด |
| 8 | ฟุตซอล/ฟุตบอล | 29 | ม.ชาญวิทย์ พึ่งอิ่ม | FUT+FBL | **ซ้ำกับชีต 7 เกือบทั้งชุด และตัวเลขไม่ตรงกัน** |
| 9-11 | เสื้อกีฬาสี (3 ชีต) | matrix | — | (หมวดใหม่) | โครงสร้างคนละแบบ: สี × ไซส์ |

**รวมประมาณ 280 แถว** จาก 8 ชีตทะเบียน

### หมวดที่ประกาศไว้แต่ไม่พบชีตทะเบียน
- **แบดมินตัน (BDM)** — ไม่มีชีต
- **วิทยาศาสตร์การกีฬา (SPS)** — ไม่มีชีต
- **สระว่ายน้ำ** และ **ศูนย์ฟิตเนส** — ไม่มีชีต ทั้งที่มีช่องลงนาม "หัวหน้าหน่วยงานสระว่ายน้ำ" และ "ผู้ประสานงานศูนย์ฟิตเนส" อยู่ในชีต 6-8

> **ต้องยืนยันกับหน่วยงาน:** ทะเบียน 4 หน่วยนี้อยู่ไฟล์อื่น หรือยังไม่เคยทำ? ถ้ายังไม่เคยทำ ควรเริ่มเก็บผ่านระบบใหม่เลยตั้งแต่ต้น

## 2. โครงสร้างคอลัมน์เดิม → ปลายทางใน Database

| คอลัมน์เดิม | ปลายทาง | ปัญหาที่ต้องแก้ตอนย้ายข้อมูล |
|---|---|---|
| ลำดับ | (ทิ้ง — ใช้ `item_id` แทน) | ซ้ำและข้ามเลขหลายจุด |
| รูปภาพ | `items.image_url` | ว่างทั้งหมด บางช่องเป็นข้อความ "ใส่รูปภาพ" |
| รายการ | `items.item_name` | บางแถวใส่ยี่ห้อแทนชื่อ ("DUNLOP", "WILSON", "AT-1008") |
| ยี่ห้อ/รุ่น | `items.brand` + `items.model` | รวม 2 ค่าในช่องเดียว ต้องแยก |
| ราคา | `item_units.purchase_price` | ว่าง ~85% |
| ปกติ | `stock_balances.qty_available` | มีข้อความปน: "1 ครบ", "15+1", "6 แผ่น", "2,000" |
| ชำรุด/ออก | **ต้องแตกเป็น 3 คอลัมน์** | ปนกัน 3 ความหมาย (ดูข้อ 4.2) |
| หมายเหตุ | **ต้องแตกเป็น 5+ ฟิลด์** | อัดข้อมูลสำคัญไว้เป็นข้อความอิสระ (ดูข้อ 3.4) |

## 3. ปัญหาคุณภาพข้อมูล (พร้อมตัวอย่างจริง)

### 3.1 จำนวนไม่ใช่ตัวเลขล้วน
`1 ครบ` · `15+1` · `6 แผ่น` · `2,000` · `-` · `ปัจจุบันตัวเล็ก 8` · `เล็ก 8 ใหญ่ 6`
→ คำนวณยอดรวมอัตโนมัติไม่ได้เลย

### 3.2 คอลัมน์ "ชำรุด/ออก" รวม 3 สถานะที่ต่างกันสิ้นเชิง
| ข้อความที่พบ | ความหมายจริง | สถานะปลายทาง |
|---|---|---|
| "ชำรุด (รอตรวจเช็ค)", "ค่อนข้างชำรุดมาก" | ยังอยู่ ซ่อมได้ | `DAMAGED` |
| "หาย 3 ตัว", "ไมค์หาย", "หาย 1 เล็ก" | สูญหาย | `LOST` |
| "จำหน่ายออก", "ทำออกแล้ว", "ทิ้งซาก", "ทิ้งไป 1ตัว" | ตัดจำหน่ายแล้ว | `DISPOSED` |

ผลกระทบ: ตอนนี้ดูรายงานแล้วแยกไม่ออกว่า "ของเสียต้องซ่อม" กับ "ของที่ไม่มีอยู่แล้ว" — ซึ่งมีผลต่อการของบประมาณคนละเรื่อง

### 3.3 ข้อมูลซ้ำข้ามชีตและขัดแย้งกัน
ชีต 7 (สนามกีฬากลาง) กับ ชีต 8 (ฟุตซอล) มีรายการชุดเดียวกันแต่ตัวเลขต่างกัน:

| รายการ | ชีต 7 | ชีต 8 | ปัญหา |
|---|---|---|---|
| รั้วกระโดดปรับได้ WT 9"/12" | ปกติ 2 / ชำรุด 7 | ปกติ 3 / ชำรุด 6 | **ขัดแย้ง** |
| เสื้อเอี๊ยมสีส้ม | ปกติ 8 | ปกติ 14 (เล็ก 8 ใหญ่ 6) | **ขัดแย้ง** |
| เสื้อเอี๊ยมสีเขียว | ปกติ 7 | ปกติ 14 (เล็ก 5 ใหญ่ 9) | **ขัดแย้ง** |
| กรวยจราจรเล็ก, เทรนนิ่งมาร์กโคน, โดมมัลติโคนส์, สปีดริง, ตุ๊กตาล้มลุก | ตรงกัน | ตรงกัน | ซ้ำซ้อน (นับ 2 รอบ) |

→ เป็นหลักฐานชัดที่สุดว่าทำไมต้องมีฐานข้อมูลกลาง: **อุปกรณ์ฝึกความคล่องตัวใช้ร่วมหลายกีฬา ไม่ควรสังกัดชีตใดชีตหนึ่ง**

### 3.4 หมายเหตุอัดข้อมูลหลายชนิดไว้ด้วยกัน
| ข้อความจริง | ควรแยกเป็นฟิลด์ |
|---|---|
| "ชั้น 3 ห้องเก็บของ ใต้ที่นั่ง" | `location_id` |
| "อยู่ห้องฝ่ายกิจกรรม", "ย้ายออฟฟิต" | `location_id` + ประวัติการย้าย |
| "Arena ยืมใช้งาน 1 ตัว ชำรุด1" | `borrow_requests` (การยืมข้ามหน่วยงาน!) |
| "เข้าปี 2566", "เข้า ต.ค. 64" | `acquisition_date` / `budget_year` |
| "ACT SPORT-03 4787" | `item_units.asset_number` |
| "เบอร์1 6ตัว เบอร์2 7ตัว เบอร์3 9ตัว เบอร์4 4ตัว" | `item_variants` (ดูข้อ 4.1) |
| "ฟองน้ำเสื่อมสภาพ (ใช้เกราะหุ้มแทน)" | `maintenance_records.problem_description` |

### 3.5 ยอดรวมเสื้อกีฬาสีไม่ตรงกัน 3 ค่า
ตาราง ป.1-ป.3: ไล่ผลรวมรายสีได้ **124 ตัว** แต่ช่อง "รวม" เขียน **80** และกล่องสรุปเขียน **81**
ตาราง ป.4-ม.6: ผลรวมจริง **41 ตัว** ตรงกับช่องรวม แต่กล่องสรุปเขียน **45**
สรุป "รวมทั้งหมด 126" ขณะที่ตัวเลขจริงคือ **165**

→ คลาดเคลื่อน ~24% เพราะพิมพ์ยอดรวมด้วยมือ ระบบใหม่ต้องคำนวณจาก transaction เท่านั้น

### 3.6 ปัญหาอื่นที่พบ
- **ไม้เทนนิสแยกรายอัน 30 บรรทัด** โดยใช้ยี่ห้อเป็นชื่อรายการ → ถูกต้องในแง่ครุภัณฑ์รายชิ้น แต่ผิดโครงสร้าง ควรเป็น `items` = "ไม้เทนนิส" + `item_units` 30 ชิ้น
- **ลำดับซ้ำ/ข้าม**: ชีตเทเบิลเทนนิสมีเลข 4 สองครั้ง, ชีตห้องเต้นมีเลข 19 สองครั้ง, ชีตฟุตซอลเรียง 8→19→18→9
- **ราคาว่าง ~85%** → ทำรายงานมูลค่าทรัพย์สินไม่ได้
- **ไม่มีเลขครุภัณฑ์เกือบทั้งหมด** → ตรวจนับทีละชิ้นไม่ได้จริง
- **ปนของที่ไม่ใช่อุปกรณ์กีฬา**: แอร์, เครื่องทำน้ำเย็น, พัดลม, ตู้ล็อกเกอร์, ปลั๊กไฟ กระจายอยู่หลายชีต

## 4. การปรับ Schema (v1 → v2)

### 4.1 [เพิ่มใหม่] ตาราง `item_variants` — รองรับ สี/ไซส์/เบอร์

ข้อมูลเดิมบังคับให้ต้องมี เพราะพบอย่างน้อย 4 กรณี:
- ชุดป้องกันตัวเทควันโด WTF → เบอร์ 1-4 (6/7/9/4 ตัว)
- เสื้อกีฬาสี → 9 สี × 7 ไซส์
- เสื้อเอี๊ยม KIPSTA → ขนาดเล็ก/ใหญ่
- ตัวจับปีนหน้าผา (Hold) → 9 สี (เหลือง 79, เทา 100, ม่วง 79, เขียว 474, ชมพู 142, น้ำเงิน 66 ...)

```
item_variants
├─ variant_id        PK
├─ item_id           FK → items
├─ variant_code      VARCHAR(30)   -- TKD-GUARD-N2, SHIRT-RED-S
├─ attribute_1_name  VARCHAR(30)   -- 'สี'
├─ attribute_1_value VARCHAR(50)   -- 'แดง'
├─ attribute_2_name  VARCHAR(30)   -- 'ไซส์'
├─ attribute_2_value VARCHAR(50)   -- 'S'
└─ is_active         BOOLEAN
```
พร้อมกันนี้ต้องเพิ่ม `variant_id` (nullable) ลงใน `stock_balances`, `stock_transactions`, `borrow_items`, `return_items`

### 4.2 [แก้ไข] แยกสถานะให้ครบ 6 ระดับ

เดิม v1 มี `AVAILABLE / BORROWED / REPAIRING / DAMAGED / LOST / DISPOSED` — ยังไม่พอ ต้องเพิ่ม 2 สถานะที่ข้อมูลจริงต้องการ:

| สถานะ | ความหมาย | ตัวอย่างจากไฟล์เดิม |
|---|---|---|
| `AVAILABLE` | พร้อมใช้งาน | — |
| `IN_USE` | ใช้งานประจำที่ (ไม่ใช่ยืม) | ทีวี, แอร์, โต๊ะสำนักงาน |
| `BORROWED` | ถูกยืมออก | "Arena ยืมใช้งาน 1 ตัว" |
| `DAMAGED_REPAIRABLE` | ชำรุด ซ่อมได้ | "เบาะ ผ้าใบขาด ชำรุดบางจุด" |
| `DAMAGED_BEYOND_REPAIR` | ชำรุด รอตัดจำหน่าย | "กิ่งหักทั้งหมด" |
| `LOST` | สูญหาย | "หาย 3 ตัว" |
| `DISPOSED` | ตัดจำหน่ายแล้ว | "จำหน่ายออก", "ทิ้งซาก" |

`stock_balances` จึงต้องเพิ่มคอลัมน์: `qty_lost`, `qty_disposed` แยกจาก `qty_damaged`

### 4.3 [เพิ่มใหม่] ตาราง `inventory_counts` — รอบตรวจนับประจำปี ★ สำคัญที่สุด

นี่คือสิ่งที่ v1 ตกไป ทั้งที่เป็นแก่นของเอกสารเดิม ระบบต้องรองรับรอบตรวจนับ + ลงนาม 3 ระดับ + พิมพ์ใบตรวจนับตามรูปแบบเดิม

```
inventory_counts                    inventory_count_items
├─ count_id        PK               ├─ count_item_id     PK
├─ count_no        'IC-2568-01'     ├─ count_id          FK
├─ fiscal_year     2568             ├─ item_id / variant_id / unit_id  FK
├─ unit_name       'เทควันโด'        ├─ qty_system        จำนวนตามระบบ
├─ count_date      DATE             ├─ qty_counted       จำนวนที่นับได้จริง
├─ responsible_user_id   FK         ├─ qty_damaged       พบชำรุด
├─ responsible_signed_at DATETIME   ├─ qty_lost          พบสูญหาย
├─ head_user_id          FK         ├─ variance          ผลต่าง (qty_counted - qty_system)
├─ head_signed_at        DATETIME   ├─ is_checked        ✓ "เช็คแล้ว"
├─ auditor_user_id       FK         ├─ note
├─ auditor_signed_at     DATETIME   └─ counted_by        FK
└─ status  DRAFT/COUNTING/
           PENDING_APPROVAL/CLOSED
```

**ฟังก์ชันที่ต้องมีเพิ่ม:**
| ฟังก์ชัน | รายละเอียด |
|---|---|
| `openCountRound()` | เปิดรอบตรวจนับ → snapshot ยอดระบบทั้งหมดของหน่วยงานนั้น |
| `recordCount()` | เจ้าหน้าที่นับจริง กรอกผ่านมือถือ/สแกน QR |
| `viewVariance()` | แสดงเฉพาะรายการที่ยอดไม่ตรง (เน้นสีแดง) |
| `signOff()` | ลงนามทีละระดับตามลำดับ (บังคับลำดับ) |
| `closeCountRound()` | ปิดรอบ → ปรับยอดระบบให้ตรงกับที่นับได้ พร้อม log `ADJUST` |
| `printCountSheet()` | **พิมพ์ PDF รูปแบบเดียวกับไฟล์เดิม** พร้อมช่องลงนาม |

### 4.4 [เพิ่ม] `responsible_unit` และผู้รับผิดชอบระดับรายการ

ไฟล์เดิมแยกความรับผิดชอบด้วย "ชีต" → ในระบบใหม่ต้องเป็นฟิลด์จริง

```
organization_units
├─ unit_id         PK
├─ unit_name       'เทควันโด', 'สำนักงานศูนย์กีฬา', 'สระว่ายน้ำ', 'ศูนย์ฟิตเนส'
├─ head_user_id    FK → users     -- หัวหน้าหน่วยงาน
└─ parent_unit_id  FK             -- สังกัดศูนย์กีฬา
```
เพิ่มใน `items`: `owner_unit_id` (FK) และ `responsible_user_id` (FK)

### 4.5 [ปรับ] รองรับการยืมข้ามหน่วยงาน/หน่วยงานภายนอก

จากข้อมูล "Arena ยืมใช้งาน 1 ตัว" และ "ที่มาจาก อารีน่า" แสดงว่ามีการหมุนเวียนของระหว่างศูนย์กีฬา ↔ อารีน่า ↔ ฝ่ายกิจกรรม

เพิ่มใน `borrow_requests`:
- `borrower_type` ENUM: `INTERNAL_USER` / `INTERNAL_UNIT` / `EXTERNAL_ORG`
- `borrower_unit_id` FK → organization_units
- `borrower_org_name` VARCHAR(150) กรณีหน่วยงานภายนอก

### 4.6 [ปรับ] หมวดหมู่ 12 → 16

เพิ่ม 4 หมวดที่ข้อมูลจริงบังคับให้ต้องมี

| รหัส | หมวดใหม่ | เหตุผล |
|---|---|---|
| `GEN` | อุปกรณ์ฝึกทั่วไป (Agility/Conditioning) | กรวย, บันไดสปีด, รั้วกระโดด, สปีดริง, มาร์กเกอร์ — **ใช้ร่วมหลายกีฬา** ต้นเหตุข้อมูลซ้ำในข้อ 3.3 |

## 6. แผนการย้ายข้อมูล (Data Migration Plan)

### ขั้นที่ 1 — ตั้ง Master Data (ทำได้ทันที)
นำเข้า `organization_units`, `sport_categories` (16 หมวด), `buildings`, `locations` (18 แห่ง), `users` (ผู้รับผิดชอบ 4 ท่านที่ปรากฏในไฟล์)

### ขั้นที่ 2 — ทำความสะอาดข้อมูล (ต้องให้เจ้าหน้าที่ยืนยัน)

| กฎ | การดำเนินการ |
|---|---|
| R1 | แปลงจำนวนเป็นตัวเลขล้วน: `"1 ครบ"`→1, `"6 แผ่น"`→6, `"2,000"`→2000, `"-"`→0 |
| R2 | `"15+1"` → แตกเป็น 2 variant: มาตรฐาน 15 + แบบอื่น 1 |
| R3 | แตกคอลัมน์ "ชำรุด/ออก" เป็น `qty_damaged` / `qty_lost` / `qty_disposed` ตามคำในหมายเหตุ |
| R4 | ดึงสถานที่จากหมายเหตุ → `location_code` |
| R5 | ดึงปีที่รับเข้า → `acquisition_year` (แปลง พ.ศ. ย่อ "64"→2564) |
| R6 | แยก "ยี่ห้อ/รุ่น" → `brand` + `model` (ตัดที่ช่องว่างแรกหรือคำว่า "รุ่น") |
| R7 | รายการที่ชื่อเป็นยี่ห้อล้วน (`DUNLOP`, `WILSON`, `HEAD`) → ตั้งชื่อ `items` ให้ถูก แล้วย้ายยี่ห้อไปคอลัมน์ brand |
| R8 | **รวมรายการซ้ำชีต 7/8** → ย้ายไปหมวด `GEN` เก็บที่เดียว แล้ว**ให้เจ้าหน้าที่นับใหม่** (ยอดขัดแย้งกัน เชื่อฝั่งใดไม่ได้) |
| R9 | ไม้เทนนิส 30 บรรทัด → `items`= "ไม้เทนนิส" 1 รายการ + `item_units` 30 ชิ้น |
| R10 | เสื้อกีฬาสี → `items` 2 รายการ (มีเซ็นต์/ไม่มีเซ็นต์) + `item_variants` (สี×ไซส์) และ**นับใหม่** เพราะยอดคลาดเคลื่อน 24% |
| R11 | รายการที่หมายเหตุว่า "จำหน่ายออก/ทำออกแล้ว/ทิ้งซาก" → นำเข้าเป็นสถานะ `DISPOSED` **ไม่ลบทิ้ง** (ต้องเก็บประวัติ) |

### ขั้นที่ 3 — สร้างเลขครุภัณฑ์
รายการ `DURABLE` ที่ราคา ≥ เกณฑ์ที่โรงเรียนกำหนด ต้องออกเลขครุภัณฑ์ + QR Code รูปแบบ `ACT-SPORT-[หมวด]-[running]` โดยยึดรูปแบบเดิม `ACT SPORT-03 4787` เป็นต้นแบบ

### ขั้นที่ 4 — นำเข้าและตรวจสอบ
Import → รันรายงานเทียบยอดกับไฟล์เดิมรายชีต → ให้ผู้รับผิดชอบแต่ละหน่วยยืนยัน

### ขั้นที่ 5 — เปิดรอบตรวจนับ 2569 ในระบบ
ใช้รอบตรวจนับครั้งแรกเป็นการ "ยืนยันยอดตั้งต้น" ไปในตัว แล้วปิดไฟล์ Google Sheets เดิม
